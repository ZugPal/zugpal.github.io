## 0. How to work through this plan

- Do the phases in order. Each phase is one commit + push to `main` (that is the deploy). Do not start the next phase before `npm test` passes (exit code 0, check it, do not trust `tail`) and you have looked at the screenshots in `review/screens/`.
- After changing ANY app file run `node tools/update-sw.js`, or phones keep the old version.
- Every new text needs German, English and Arabic in `src/i18n.js` (same key in all three, insert before `joinTalk:` as the earlier texts were). Arabic is RTL: check the AR screenshots.
- Keep the product principles in `CLAUDE.md` section 2, except the one change Husam decided in this plan (phase 3: the receiver sees who waved).
- Demo mode (`?demo`) must keep working for every new feature, so the Playwright tests can cover it.
- Database changes: write a migration in `supabase/migrations/`, dry-run it with the Supabase connector (`execute_sql` ending in `raise exception`), then `apply_migration`. New security-definer helpers go in the `private` schema; revoke every new function from `PUBLIC` and `anon`. Add the result to `supabase/schema.sql`.
- Never put the `service_role` key or the database password into code, commits or chat. Codes only as bcrypt hashes.
- Ask Husam before anything irreversible. The open questions are collected in section 12; everything else is decided here.

## 2. Phase 1: fix what is broken on the phone (first, small, one commit)

1. **Typing must never lose letters.**
   - Rule: a background refresh (poll, Realtime, toast) may never replace a focused input or textarea.
   - Implement in `src/screens.js`: `render()` gets a cheap path for the chat screen. When `S.screen === "chat"` and the rebuild was triggered by `poll()`/`onRealtime()`/`toast()` (pass a flag, e.g. `render({ soft: true })`), only patch: `#chatLog` innerHTML (and scroll to bottom if the user was at the bottom), the header "Active now" line, the unread badges. Do not touch the composer (`#chatInput`, toolbar).
   - Do the same soft path for every screen that has a focused `INPUT`/`TEXTAREA`/`SELECT`: if `document.activeElement` is one of those and the render is soft, skip the rebuild and set `S.renderPending = true`; run the full render on `blur` or after sending (wire in `src/main.js`).
   - Move the toast out of `#app` (its own `#toast` element in `index.html`), so a toast never re-renders a screen.
   - Change `#chatInput` to a `<textarea rows="1" enterkeyhint="send">` that grows to 4 lines; Enter sends on desktop, the send button on phones.
   - Test (`tests/chat-typing.spec.js`): type 40 characters with `page.keyboard.type(text, { delay: 30 })` while a poll fires (call `poll()` via `page.evaluate` in the middle); the input must contain the full text.
2. **Phone back button** (`src/nav.js`, new).
   - Every screen change through `actions.go`/`openX` calls `pushScreen(name)` → `history.pushState({ z: ++n, screen }, "")`. `popstate` → if a sheet/overlay/viewer is open, close it; else show the previous screen (`S.screen = e.state.screen`) without pushing again. On the root screens (check-in, people list when checked in) one more back exits the app, as Android users expect.
   - Deep links `#talk`, `#ride-CODE`, `#train-CODE` (phase 5) keep working: read them at start-up, then `history.replaceState`.
   - Test: go check-in → games → chess, `page.goBack()` twice, expect the check-in screen.
3. **"Add to calendar" on Android.**
   - Primary button stays Google Calendar (`googleLink()` worked). The `.ics` button: if `navigator.canShare && navigator.canShare({ files: [file] })` use `navigator.share({ files: [new File([ics], "zugpal-talk-train.ics", { type: "text/calendar" })], title })` so the Android share sheet offers the calendar app. Otherwise download as today and show the hint "Open the downloaded file to add it" (new text `calOpenHint`).
4. **Notification without names.** `notify()` in `src/polling.js`: title `Zugpal`, body `t("newMsgsN", { n })` ("1 new message" / "3 new messages"), icon `icons/icon-192.png`, badge a monochrome `icons/badge-96.png` (make it: white Z on transparent). Remove `newMsgFrom` from the notification path (keep it for in-app toasts if used elsewhere).
5. **Start-up when still checked in** (`src/main.js:74`). Still go to the people list, but show a slim bar on top of it: "You're on RE 1 · 07:42 · Leave" (`S.ride.label`, button `leave`). ## 5. Phase 4: bad network on trains, honest plan

What can be done in a web app (do this):

1. **Outbox** (`src/outbox.js`): every outgoing chat message, wave, check-in and game move is written to IndexedDB first (`zugpal-outbox`), shown immediately in the chat with a grey clock, then sent. Retry with backoff 2 s, 5 s, 15 s, 60 s and on `online` events. Sent → one tick; the partner's `seen_at` newer than the message → two ticks (needs no new column: `riders.seen_at` already exists; show "read" only loosely as "seen since"). Never drop a message; if it fails for 10 minutes, show "Not sent · Retry".
2. **Read offline**: cache the last 50 messages per chat and the match list in IndexedDB (`zugpal-chat`). When the app opens offline, the chats are readable, with the "Reconnecting…" bar on top.
3. **Short timeouts**: wrap Supabase calls in an 8 s `AbortController` timeout; a hung request on a dying connection is worse than a failed one. Realtime reconnects on `online`/`visibilitychange`.
4. **Fewer requests**: after reconnect fetch only messages with `id > last seen` (add `.gt("id", lastId)` where the loader lists messages; check `src/chat.js loadMessages`).
5. **Offline games**: everything vs computer and "two players on one phone" must open offline. Verify all 10 games and the word lists are in `sw.js` FILES (run the app with Playwright `context.setOffline(true)` in `tests/offline.spec.js` for each game). Online games queue moves in the outbox; the board shows "Waiting for connection" instead of an error.
6. **Captive WLAN**: if a fetch returns HTML or a redirect (train WLAN login page), show "Train WLAN needs a login: open the browser once" (`netPortal`).

What cannot be done in a web app, say it plainly to Husam:

- **Bluetooth between phones.** Browsers cannot discover other phones over Bluetooth (Web Bluetooth only talks to peripherals, Chrome/Android only, and a phone cannot act as a peripheral from a web page). So "someone in your coach" and phone-to-phone chat without internet need the **native app** (Android: Nearby Connections / Wi-Fi Aware; iOS: Multipeer Connectivity). That native app would be the real answer to bad train internet: two phones in the same coach could wave and chat with zero network. Keep it as roadmap item 8, and make the web app's outbox good enough until then.
- A page cannot keep running once Android kills the browser tab; background notices stay best-effort (phase 1 already says "while Zugpal is open in the background").

## 6. Phase 5: your own train (groups), replaces the fixed Talk Train config

Husam's request: instead of a fixed Talk Train in `src/config.js`, people (or Husam) create a train, and it works like a group where everyone can talk together.

Decided design (ideas Husam can still change, see section 12):

- **Trains people create** (`public.trains`): `code` (6 chars, in the link `#train-CODE`), `label` ("RE 1 · 07:42 · Düren → Köln"), `weekday` or single `date`, `time`, `minutes`, `coach` optional, `women_only`, `theme` (talk / German practice / games / coffee), `created_by`, `created_at`. Anyone with a profile can create one; max 3 active trains per user. Husam's Talk Train becomes just the first train, created by him, marked `featured` by a host (`hosts` table exists). `CONFIG.talkTrain` is kept only as the fallback when the trains table is empty (demo mode).
- **List on the check-in screen**: "Trains with Zugpal people": upcoming trains sorted by next departure, with the count of people who said "I'll be there" (`train_members`), "Add to calendar", "Join". The next featured train keeps the big hero.
- **Group chat per train ride** (`public.group_messages`: `ride_key`, `from_user`, `body`, `created_at`): everyone checked in on that ride (same `ride_key`, so also for ad-hoc trains `LINE-NUMBER-DATE`) can read and write. One room per ride, deleted with the ride by `private.cleanup()`. RLS: `exists (select 1 from riders where id = auth.uid() and ride_key = group_messages.ride_key)`; blocked people's messages filtered with `private.can_see()`. Women-only trains: only women can check in (`riders.gender = 'woman'`), enforced in the check-in function, not only in the UI.
- Group chat UI: tab "Everyone" next to the people list; messages with first name + blurred photo; long-press → Report (reuses `file_report()`, add `kind = 'group'`), Mute person (local). The host (creator) can remove a message (`private` function, logged). Contact details blocked as in 1:1 chat. No photos/voice in the group for now (safety, size).
- Waves and 1:1 chat stay as they are; the group is the "everyone talks together" layer.
- QR per train from phase 2 (`qr.html?code=`).
- Demo mode: one demo train with 4 simulated people and a few group messages.
- Tests: create a train in demo mode, see it in the list, join it, write in the group.

Other ideas to offer Husam (not built unless he picks them):
- "Open a table": during any ride, one person opens a themed table ("German practice at the window seats, coach 5") that others on the same ride can join; shows up as a card in the people list.
- "Regulars": "I take this train every weekday" → the app lists how many regulars are on your usual train (numbers only, no names), to show a newcomer the train is not empty.
- Weekly themes set by the host ("This Tuesday: bring a photo of your hometown") shown as an announcement in the group.
- Partner trains: a company or university creates a train for its people (code only, no public listing).

## 7. Phase 6: chat like WhatsApp

Goal: simple, familiar, nothing to learn. Keep all safety features visible.

Do (in this order, one commit each if large):

1. **Layout**: bubbles with time, grey clock / one tick / two ticks (from phase 4), day separators, "Today", unread divider, sticky date header, long-press menu on a bubble: Reply, Copy, Report. Reply quoting (`re:<msgid>` prefix inside the body, rendered as the quoted line). Reactions with the existing positive `REACT` set only.
2. **Composer**: one text field, a `+` button that opens a sheet (Photo, Camera, Voice note, Video, Game, Story, German word), a microphone button that records while held (hold-to-record, slide to cancel) and shows the waveform/time. The chip row is removed; "Topic dice", "Who asks next", "Two truths" move into the `+` sheet under "Icebreakers".
3. **Media on Supabase Storage** (migration): bucket `media`, path `<ride_key>/<uuid>`, RLS so only the two matched users can read, signed URLs for 10 minutes, auto-delete after 24 h by `private.cleanup()` (list objects older than 24 h via `storage.objects`). Move photos and voice from base64 in Postgres to this bucket (keep reading old rows until they expire). Then add **video messages**: `MediaRecorder` with `video/webm;codecs=vp8` or `video/mp4` on iPhone, max 30 s, 480p, 8 MB cap, shown with a poster frame. Keep the rule: media arrives blurred/locked until both have sent 2 text messages; view-once stays the default and a "keep" option is NOT added (safety).
4. **Normal photos after a match?** Husam wants pics "like WhatsApp". Decision: photos stay view-once (24 h) in 1:1 chats; this is a safety feature, explain it in the chat empty-state ("Photos here disappear after viewing").
5. **Calls (voice, video)**: WebRTC between the two matched people, signalling over the existing Supabase Realtime channel (`call:<gid>` broadcast with offer/answer/ICE), STUN `stun:stun.l.google.com:19302`, plus a **TURN server** (without TURN most calls on mobile networks fail). TURN options: Metered.ca free tier (50 GB/month, EU region) or Cloudflare Calls TURN; keys go in `src/config.js` like the anon key only if they are public-safe, otherwise an Edge Function hands out short-lived TURN credentials. Rules: calls only between matches, only after 2+ text messages each, "Report" available during and after, no numbers ever exchanged, ring 30 s max, both sides see a big "End" button. Build voice calls first, video after voice works between an Android and an iPhone on mobile data. Honest expectation to tell Husam: on a moving train calls will drop often; voice notes are the reliable version of the same thing.
6. Tests: typing test from phase 1 extended, `+` sheet opens, hold-to-record UI appears (no real mic in Playwright), video message card renders from a fake row in demo mode.
